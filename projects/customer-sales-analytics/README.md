# Customer Status and Sales Reconciliation

## Business problem

Customer records, sales, and refunds can come from different sources. The
analyst needs to organize customer statuses and reconcile transactions by
representative so sales activity can be reviewed for commission payments.

## My contribution

In the original work, I prepared and combined customer and transaction data,
reviewed customer statuses, checked records for duplicates, and created
representative-level sales and funding reports. The operational work used
Python, pandas, spreadsheets, and SQL-based data sources.

## Illustrative workflow

1. Review customer records and separate active, pending, and cancelled
   statuses.
2. Link sales to customers and representatives using IDs.
3. Join sale and refund transactions to each sale and calculate net sales.
4. Group net sales by representative for review. In this example only,
   multiply net sales by the fictional rate in `representatives.csv`.

## Executable ETL Demonstration

This independently created demonstration is inspired by general analytical
workflows. It is not original company software, and its fictional data,
policies, rates, and results do not describe an actual business.

### Business Problem

Sales and customer records may contain missing or inconsistent identifiers,
while refunds can change the amounts available for reconciliation. A
reviewer needs a transparent view of both the valid transactions and the
exceptions before using the information to support payment decisions.

### Project Objective

Generate a small fictional dataset, validate relationships and data
quality, and produce representative-level reconciliation reports that make
excluded records visible. The demonstration is not a payroll system.

### Tools and Technologies

- Python 3.10 or later; pandas for validation, joins, and aggregation.
- openpyxl for the Excel workbook and chart; pytest for automated tests.
- CSV files for inputs and reviewable outputs.

### Synthetic Dataset Description

The generator in [pipeline.py](demo/pipeline.py) creates fixed, invented
customers, representatives, sales, and transactions. It uses identifiers
such as `C001` and `TXN001` rather than names or contact information.
Fictional statuses include active, pending, and cancelled; transactions
include sales and refunds. Some records deliberately have missing IDs,
duplicate IDs, inconsistent or invalid statuses, invalid amounts, and
unmatched or invalid relationships. Rates and amounts are invented.

These inputs are newly generated by the demo and are separate from the
earlier case-study CSV files in [data/](data/). The two examples have
different fictional records and totals.

### ETL Workflow

1. **Generate and extract:** create four synthetic CSVs in a new output
   directory, then read them as strings. Check the headers and record widths.
2. **Validate:** identify missing required fields, duplicate identifiers,
   unsupported statuses and transaction types, invalid amounts and rates,
   and missing or invalid related records.
3. **Transform:** trim whitespace; normalize IDs to uppercase and statuses
   and transaction types to lowercase; join valid records using checked
   identifiers. Exclude every row with an exception and any dependent row
   that references an invalid record. Record every exclusion reason.
4. **Report:** export validated sales and transactions, an exception list,
   and representative summaries to CSV and a formatted Excel workbook.
   The workbook includes a chart of fictional gross, refund, and net amounts.

### Data Quality Checks

`exceptions.csv` and the workbook's **Exceptions** sheet contain an entity,
source CSV row number, record ID (blank if missing), field, and reason.
Duplicate IDs are all excluded, not arbitrarily deduplicated. A transaction
is also excluded if its sale is absent or invalid. Invalid values are not
silently repaired. Each exception is an issue, so one record can have more
than one. The report is for manual review.

### Reconciliation Logic

Valid `sale` transaction amounts must be positive; valid `refund` amounts
must be negative. Gross is the sum of sale transactions; refunds are the
sum of negative refund transactions; net is gross plus refunds. The
fictional commission is net multiplied by a fictional representative rate,
rounded to two decimal places using half-up rounding. Input amounts may
have at most two decimal places; arithmetic uses integer cents and Decimal.

A cancelled sale does **not** automatically generate a refund. This demo
includes a sale transaction and an independently recorded refund for one
cancelled sale. Transactions with exceptions are excluded, so reported
totals may be incomplete until the exceptions are reviewed. A validated sale
with no valid transaction is still counted, with a transaction count of zero.

### How to Run

Open the repository folder in VS Code. In a PowerShell terminal at the
repository root, install the dependencies in a local virtual environment:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r .\projects\customer-sales-analytics\demo\requirements.txt
.\.venv\Scripts\python.exe .\projects\customer-sales-analytics\demo\pipeline.py
```

The command creates `projects\customer-sales-analytics\demo\generated\`
only if that directory does not already exist. It never overwrites an
existing output directory. To run again, specify a new path, for example:

```powershell
.\.venv\Scripts\python.exe .\projects\customer-sales-analytics\demo\pipeline.py --output-dir .\projects\customer-sales-analytics\demo\generated\run-2
```

Open `generated\fictional_reconciliation.xlsx` in Excel. The directory
also contains `synthetic_inputs\`, `validated_sales.csv`,
`validated_transactions.csv`, `reconciliation_summary.csv`, and
`exceptions.csv`. The workbook contains **Read Me**, **Validated Sales**,
**Valid Transactions**, **Reconciliation**, and **Exceptions** sheets.
Generated files in the default `generated` directory are ignored by Git.

### How to Run Tests

From the repository root, after installation:

```powershell
.\.venv\Scripts\python.exe -m pytest -q .\projects\customer-sales-analytics\demo\tests
```

The tests cover validation, joins, exceptions, rounding, cancellation
behavior, output protection, and reproducibility. CSV content and workbook
sheet values are reproducible; Excel archive metadata may differ between runs.

### Assumptions and Limitations

All data fits in memory. This example does not model dates, payment
eligibility, chargebacks, multiple currencies, authorization, real
commission policies, or transaction-level matching against sale amounts.
Statuses and rate ranges are illustrative. It uses a simplified
representative-level net calculation and is not suitable for real payroll
or production decisions without agreed business rules and independent
validation. Grouped cent totals use signed 64-bit integers; Excel numeric
cells also have limited precision. Individual transaction amounts outside
the supported range are reported as exceptions, and the pipeline stops
with an error if a representative's gross or refund total exceeds that
range. The small fictional sample stays within those limits.

### Data Privacy Statement

The executable demo generates only invented identifiers and values; it does
not access the older sample files or any company systems or credentials.
Do not upload customer data, confidential documents, credentials, or
proprietary code. Review any future files and generated outputs before
publishing, even when a repository or directory is ignored by Git.
